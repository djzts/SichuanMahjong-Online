# 任务：四川麻将（血战到底）在线网页游戏 —— 方案一（GitHub Pages + PeerJS P2P，房主权威）

你在一个空的 Git 仓库（djzts/SichuanMahjong-Online）里工作。请从零开发一个可以部署在 GitHub Pages 上的四人在线四川麻将（血战到底）网页游戏，每个房间另外带 2 个观战位。这是给熟人朋友玩的：没有后端服务器、没有账号系统、不涉及真钱。

## 1. 技术方案
- 前端：Vite + TypeScript（strict），UI 用原生 DOM 或 Preact，不用重型框架；构建产物是纯静态文件。
- 用 hash 路由（或单页、不用路由），避免在 GitHub Pages 上刷新时出现 404。
- Vite 的 base 设为 '/SichuanMahjong-Online/'（可以用环境变量覆盖），本地和线上都能正常加载资源。
- 联机：PeerJS（WebRTC P2P），默认使用 PeerJS 官方的免费信令服务器；信令服务器的 host/port/path 做成可配置。
- Peer ID 加前缀，避免和陌生人冲突，例如房主 ID = `scmj-<房间码>`。
- ICE：默认使用公共 STUN，并在 src/config 里预留 TURN 字段（urls / username / credential）。README 里要说明：放在静态站点里的 TURN 凭据是公开的。
- 架构：房主权威。房主浏览器负责洗牌、发牌、规则判定、计分和状态推进；其他玩家只发送操作意图（出牌、碰、杠、胡、过、换三张选牌、定缺），房主校验后广播结果。非法或过期的消息直接拒绝，并给该客户端回一个错误提示。
- 房主自己的操作也走同一套「意图 → 校验 → 广播」流程（本地直连，不经过网络），让单机和联机共用一套代码。
- 信息隐藏：所有发给客户端的数据，都只能通过一个纯函数 viewFor(state, viewer) 按接收者生成，这是唯一的出口。
  - 发给玩家：只有他自己的手牌；别人的信息只发公开部分（牌河、副露、手牌数量、定缺、是否已胡、牌墙剩余张数）。换三张时换出去的牌、暗杠的牌，别人都看不到。
  - 发给观战者：见第 2 节「观战位」。
- 随机数：洗牌用可以设种子的 PRNG（种子由房主生成），方便测试和复现；每局记录操作日志，可以用「种子 + 日志」重放一局。
- 代码标识符和注释用英文；界面文案用中文，集中放在一个文案文件里。

## 2. 房间流程
- 首页：输入昵称 → 「创建房间」（生成 6 位纯数字房间码，方便手机输入；如果 Peer ID 已被占用就重新生成）或「输入房间码加入」。加入时选择「入座」或「观战」。
- 等待室：显示 4 个玩家座位和 2 个观战位。房主可以把空的玩家座位设为电脑 AI，也可以移除 AI；四个玩家座位都坐满后，房主点「开始」（观战位空着也能开始）。页面显示房间码，并提供「复制邀请链接」和「复制观战链接」（链接里带房间码，打开后直接进入入座或观战流程）。
- 支持多局连续对局，显示每人的累计积分和每局记录；房主可以结束牌局，结束时显示总排名。
- 庄家（默认值，可配置）：第一局随机定庄，或由房主做庄；之后由上一局第一个胡牌的人做庄；如果上一局第一次胡牌是一炮多响，由点炮者做庄；流局时原庄家连庄。
- 身份与断线重连：
  - 每个客户端第一次打开时生成一个 playerId（UUID），存在 localStorage 里；房主用 playerId → 座位（玩家座位或观战位）的映射来识别客户端，昵称只用来显示，也作为兜底匹配。
  - 客户端刷新或断线后，用同一个房间码自动重连，回到原来的玩家座位或观战位，房主按它的身份发一份完整的状态快照。
  - 玩家断线期间由 AI 托管（界面上标「托管中」），重连后恢复手动操作。
  - 房主断线时，其他客户端（包括观战者）显示「房主已断开，游戏暂停」，并持续尝试重连。
  - （可选加分项）房主把对局状态快照存在 localStorage 里，房主刷新页面后，可以用同一个房间码恢复房间和对局。注意 PeerJS 服务器可能会把旧 ID 再占用一小段时间，需要重试。

### 观战位
- 除了 4 个玩家座位，每个房间另有 [2] 个观战位（数量可配置）。玩家座位满了只能选观战；观战位也满了就提示「房间已满」。
- 开局前和对局进行中都可以进来观战；中途进来时，房主发一份当前的观战快照。
- 观战者只能看到四家的牌河（打出的牌，按出牌顺序；牌河的显示方式和玩家看到的一致），以及不涉及牌面的状态：座位和昵称、当前轮到谁、牌墙剩余张数、谁已经胡牌、每家累计积分和每次结算的得失分。
- 观战者看不到：任何一家的手牌（包括胡牌时亮出的手牌和流局时的手牌）、换三张的牌。这一条是硬性要求，不做成开关。
- 下面几项默认也不给观战者看，做成配置开关 [全部关闭]：副露、定缺、手牌张数、结算时的牌型和番型明细。
- 隐藏必须在房主端完成：房主根本不把这些数据发给观战者，不能只靠前端不显示。因为 P2P 下，观战者在浏览器开发者工具里能看到自己收到的全部数据。
- 观战者不能发送任何游戏操作，房主收到直接拒绝。观战者不参与积分，不会被 AI 托管；观战者断线不影响对局，也不触发暂停。
- 开局前，客户端可以在玩家座位和观战位之间切换；开局后观战者只能观战，不能中途上桌。房主可以移除观战者。
- 玩家界面显示当前有几个观战者以及他们的昵称。

## 3. 规则（全部集中在一个 rules config 对象里，可配置；方括号里是默认值）
### 牌与发牌
- 108 张：万、条、筒各 1–9，每种 4 张；没有字牌、没有花牌。
- 庄家 14 张，其余三家各 13 张。行牌按逆时针顺序：你的下家坐在你右手边。
- 杠牌后从牌墙尾部补一张。牌墙没牌时不能再杠。

### 换三张 [开启]
- 发完牌后，每人选 3 张同一花色的牌；交换方向随机：顺时针 / 逆时针 / 对家。
- 所有人都选好后同时交换。超时 [20] 秒，自动从至少有 3 张、且张数最少的那一门里选 3 张。

### 定缺
- 换完三张后，每人选一门作为缺门，所有人选好后同时公布。超时就自动选张数最少的一门。
- 手上有缺门的牌时，必须先打缺门的牌。
- 手上还有缺门的牌时不能胡。
- 不能碰、杠缺门的牌。

### 碰、杠（不能吃）
- 杠分三种：明杠（直杠，杠别人打出的牌）、暗杠（自己摸齐 4 张）、补杠（加杠，在自己碰过的牌上补第 4 张）。
- 刮风下雨 [开启]，杠牌立即结算（单位是底分）：
  - 明杠：点杠的人付 2；
  - 补杠：其他每个还没胡牌的玩家各付 1；
  - 暗杠：其他每个还没胡牌的玩家各付 2；
  - 补杠被抢杠胡时，这个补杠不算数，也不收钱。
- 呼叫转移 [开启]：杠后补牌再打出的牌点了炮（杠上炮），这个杠收到的杠钱转给胡牌的人。一炮多响时怎么分，写进 README 的规则假设里。

### 胡牌
- 胡牌牌型：4 组面子（刻子或顺子，副露也算）+ 1 对将；或者七对（必须没有副露）。
- 胡牌方式：自摸、点炮、抢杠胡（只能抢补杠，暗杠不能抢）。
- 一炮多响 [允许]：多人胡同一张牌时都算胡，点炮的人分别付给每个胡家。
- 过水不胡 [开启]：放弃胡别人打出的牌之后，在自己下次摸牌前，不能再胡别人打出的牌（自摸不受影响）。
- 血战到底：胡牌的人退出本局（对其他玩家亮出手牌，不再摸牌、打牌），其余人继续，直到三家胡牌或牌墙摸完。
- 已经胡牌的玩家之后不再付任何钱（不付杠钱、不付自摸钱），已经赢到的分保留。

### 番型（番数做成可配置表）
- 平胡 0、对对胡 1、清一色 2、七对 2、龙七对 3、清对 3、清七对 4、清龙七对 5、金钩钓 1、带幺九 2、将对 3。
- 叠加规则：组合番型替代它的组成部分，不重复计算（例如清对算 3 番，不是清一色 2 番 + 对对胡 1 番）；只取最高的一个牌型番，再加上下面的附加番。
- 根：手里每有 4 张一样的牌（杠的、或手里藏着的 4 张都算）就 +1 番；龙七对里组成「龙」的那 4 张不再重复算根。
- 附加番：杠上花 +1、杠上炮 +1、抢杠胡 +1、海底捞月 +1、海底炮 +1。
- 天胡、地胡：直接封顶。
- 如果对某个番型的具体定义拿不准（比如金钩钓是否同时算对对胡、带幺九怎么判定），按最常见的成都规则实现，并写进 README 的「规则假设」。

### 计分
- 每个付钱的人付：底分 × 2^min(番数, 封顶番数 [3])。
- 自摸 [加底]（可以配置为「加番」）：加底就是每个付钱的人在上面基础上再多付 1 个底分（先封顶，再加底）；加番就是番数 +1（先加番，再封顶）。
- 自摸时，其他所有还没胡牌的玩家都要付；点炮时只有点炮的人付。
- 每次结算、每一局的得失分加起来都必须是 0（零和）。

### 流局（牌墙摸完）
- 只在流局时还没胡牌的玩家之间结算 [默认，可配置]：
  - 查花猪：手上还有缺门牌的人是花猪，要付给每个不是花猪的玩家封顶分；
  - 查大叫：没听牌（且不是花猪）的玩家，要付给每个听牌玩家「该听牌玩家可能胡到的最大番」（含根，不含自摸、杠上花等附加番，受封顶限制）；
  - 退税 [开启]：没听牌的玩家和花猪，要把本局收到的杠钱全部退给当初付钱的人。

### 操作优先级与时限
- 胡 > 杠 / 碰。有人打出一张牌后，房主收集所有有权响应的玩家的选择（或者等到超时），再统一裁决，不按先到先得。
- 别人打牌后的响应时间 [10] 秒，超时自动「过」。
- 自己回合 [20] 秒，超时自动打牌：有缺门的牌先打缺门的牌，否则打最右边的牌。
- 所有时限都可以配置，本地调试时可以关掉。

## 4. 电脑 AI（运行在房主端）
- 简单但合理：换三张从张数最少的一门里选；定缺选张数最少的一门；有缺门的牌先打缺门的牌；按向听数（以及有效进张数）选择出牌；能胡必胡。
- 碰杠做基本判断：不破坏清一色；听牌后要谨慎，只在不降低听牌质量时才碰杠；不碰缺门的牌。
- AI 和人类玩家走同一套「意图 → 校验」接口，不能看别人的手牌。
- AI 操作加 0.5–1.5 秒的随机延迟，免得太快、人看不清。

## 5. 界面
- 俯视牌桌：自己在下方，下家在右，对家在上，上家在左。其他三家显示手牌背面数量、副露、牌河、定缺标记、已胡标记、托管或断线状态；桌子中间显示剩余张数、当前该谁操作，以及倒计时。
- 观战视图：四家的牌河按座位排在牌桌四边，配上昵称；不显示手牌区域。默认以房主为下方，观战者可以切换视角。顶部标「观战中」，没有任何操作按钮。
- 牌面用 SVG 或 CSS 自己画（不用任何有版权的素材），万、条、筒要一眼能分清；缺门的牌、可以打的牌、刚摸到的牌，要有明显区分。
- 能操作时高亮按钮：碰、杠、胡、过（有多种杠法时让玩家自己选）；出牌支持「点一下选中、再点一下打出」，也支持拖拽。
- 结算弹窗：每次有人胡牌，显示胡牌的人、牌型、番型明细、每家得失分；一局结束时显示本局汇总和累计积分。观战者的结算弹窗只显示得失分（除非打开了对应的配置开关）。
- 手机竖屏、横屏都能玩（优先横屏），支持触屏；电脑浏览器也能玩。
- 中文界面。
- 调试模式：网址带 ?debug=1 时，可以指定随机种子、显示所有人的手牌（仅限单机）。

## 6. 代码结构与质量
- 规则引擎（牌的表示、胡牌判定、听牌与向听数、番型计算、计分、流局结算）写成与 UI、网络无关的纯函数模块，放在单独的目录里（例如 src/engine）。
- 游戏状态推进写成纯 reducer：(state, action) → 新 state + events，房主端和单机版共用。
- 用 Vitest 给规则引擎写充分的单元测试，至少覆盖：
  - 各种胡牌牌型和番型；七对、龙七对、清龙七对；根的计算（杠也算根，龙七对不重复计根）；
  - 手上有缺门的牌不能胡；不能碰缺门的牌；
  - 抢杠胡（被抢的补杠不收钱）、一炮多响、过水不胡、杠上炮呼叫转移；
  - 查花猪、查大叫、退税、封顶、自摸加底 / 加番；
  - 血战中已经胡牌的玩家不再付钱。
- 给 viewFor 写单元测试，在对局的每个阶段（换三张、定缺、行牌、有人胡牌后、结算、流局）都检查：
  - 玩家视图里只有自己的手牌，没有别人的手牌和换三张的牌；
  - 观战视图序列化成 JSON 之后，里面出现的牌只能是牌河里的牌，张数正好等于牌河总张数；配置开关关闭时，不包含副露、定缺、手牌张数和番型明细；
  - 观战者发来的任何游戏操作都会被拒绝。
- 不变量测试：用 4 个 AI 以固定种子自动对局至少 1000 局，不能抛异常；每局得失分加起来为 0；任何时刻，所有地方的牌加起来始终是 108 张。
- 网络消息要有明确的 TypeScript 类型定义和协议版本号；版本不一致时提示用户刷新页面。
- 配置 ESLint + Prettier；npm run test、npm run build、npm run lint 都必须通过。
- README 写清楚：本地运行、部署步骤（包括在仓库 Settings → Pages 里把 Source 设为 GitHub Actions）、怎么配置 TURN 和自定义 PeerJS 服务器、规则配置说明、观战可见范围的配置说明、规则假设列表。

## 7. 开发顺序（每完成一步：跑测试和构建，提交一个 commit，向我汇报进度和下一步计划）
1. 规则引擎 + viewFor + 测试。验收：测试全部通过，并覆盖上面列出的场景。
2. 单机版：我对 3 个 AI，能连续打完多局，累计积分正确。验收：我手动打完至少 2 局，1000 局 AI 自对局测试通过。
3. PeerJS 联机：开房、加入、观战、AI 补位、同步、信息隐藏、断线重连、托管。验收：同一台电脑开 6 个浏览器标签页（4 个玩家 + 2 个观战）能打完一局；观战页只显示牌河，在开发者工具里看收到的消息也没有手牌；第 7 个人加入时提示房间已满；刷新玩家或观战者的页面后，能回到原来的位置。
4. 界面打磨与手机适配（包括观战视图）。
5. GitHub Actions 部署：push 到 main 自动构建并发布到 GitHub Pages（使用官方的 actions/configure-pages、actions/upload-pages-artifact、actions/deploy-pages）。

如果规则有歧义，先按上面的默认值实现，并在 README 里列出你做的假设。
